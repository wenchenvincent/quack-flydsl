# Fused Gradient Accumulation for AMD Linear — Implementation Plan (G2)

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development or superpowers:executing-plans. Design-level; expand to TDD tasks before executing.

**Goal:** Add an optional `fuse_grad_accum` to `quack/amd/linear.py`'s training autograd path that accumulates `dW` straight into `weight.grad` instead of returning a fresh tensor for PyTorch's default grad-accumulation to add — mirroring NVIDIA's `quack/linear.py` feature of the same name.

**Architecture:** NVIDIA's `fuse_grad_accum` (`quack/linear.py:48-62`) works because `gemm_add_inplace` (`quack/gemm_interface.py:783-835`) is a real fused in-place GEMM-add kernel: `out = alpha * A @ B + beta * out`. AMD's `dW` kernel, `gemm_tn` (`quack/amd/gemm_gfx950_tn.py:694-...`), has no such mode today — its writeback is a plain store (`gemm_gfx950_tn.py:534-548`: `C_.vec_store(...)`, not a read-add-store), even though its public signature already accepts an `out: Optional[Tensor]` parameter (`gemm_gfx950_tn.py:694`) that currently only controls *where* the result is written, not whether it's added. This plan adds a compile-time `accumulate: bool` flag to the TN kernel's epilogue (read-add-store instead of store when set), and wires `LinearFunc`/`LinearActFunc` in `quack/amd/linear.py` to use it when `fuse_grad_accum=True` and `weight.grad` already exists — falling back to a torch in-place `.add_()` when the kernel-level flag isn't available for the current shape/dtype, so the feature is always correct even before every code path supports the fused kernel mode.

**Tech Stack:** `quack/amd/linear.py` (`LinearFunc`, `LinearActFunc`, `linear_train`, `linear_act_train`), `quack/amd/gemm_gfx950_tn.py` (`gemm_tn`, `_gemm_tn_out`, `_compile_tn_kernel`), `quack/amd/linear_training.py` (read for consistency — check whether it needs the same flag threaded through), `tests/amd/test_linear_train.py`. NVIDIA reference: `quack/linear.py:31-62` (`linear_fwd_postprocess`, `linear_bwd_compute_weight_grad`), `quack/gemm_interface.py:783-835` (`gemm_add_inplace`).

## Background

NVIDIA's `fuse_grad_accum` mechanism, precisely: `LinearFunc.forward` (`quack/linear.py:155-177`) stashes `ctx.fuse_grad_accum` and, in `linear_fwd_postprocess` (`quack/linear.py:31-37`), saves the *original* (pre-reshape) `weight` tensor (`weight_og`) alongside `x`/`weight` whenever `ctx.fuse_grad_accum` is set — this is needed because `weight_og.grad` (the PyTorch-managed `.grad` attribute, which only exists on leaf tensors, not on the `weight.reshape(...)`'d view used internally) is where the accumulation target lives. In `backward`, `linear_bwd_compute_weight_grad` (`quack/linear.py:48-62`) checks `ctx.fuse_grad_accum and weight_og.grad is not None and not torch.compiler.is_compiling()`; if all hold, it calls `matmul_inplace_fn(dout.T, x, weight_og.grad)` (i.e. `gemm_add_inplace`, accumulating directly into the existing `.grad` buffer) and **returns `weight_og.grad` as `dweight` while setting `weight_og.grad = None`** (`quack/linear.py:57-59`) — the `= None` is critical: it prevents PyTorch's autograd engine from *also* adding the returned `dweight` on top of the already-updated `.grad` (which is what autograd normally does with a function's returned gradient), i.e. this hijacks the accumulation to happen exactly once, inside the fused kernel, instead of once inside the kernel and once again by autograd.

AMD's `quack/amd/linear.py` has no `fuse_grad_accum` anywhere (`grep -n fuse_grad_accum quack/amd/linear.py quack/amd/linear_training.py` returns nothing). `LinearFunc.backward` (`linear.py:288-310`) always computes a fresh `dweight = gemm_tn(dout2, x)` (`linear.py:308`) and returns it — every backward pass, PyTorch's default accumulation (`weight.grad += dweight` or `weight.grad = dweight` on first call) is the only accumulation path, meaning every micro-batch step pays a full `(out, in)`-shaped tensor allocation for `dweight` that then gets added into `.grad` by autograd's own (also real, but separate) add. `LinearActFunc.backward` (`linear.py:409-434`) has the identical pattern at line 425. `gemm_tn` (`gemm_gfx950_tn.py:694-...`) already takes an optional `out: Optional[Tensor]` (used by its `_gemm_tn_out` custom op, `gemm_gfx950_tn.py:666-686`, via `mutates_args=("out",)`), but the kernel's writeback (`gemm_gfx950_tn.py:534-548`) is `cs_[lds_m_idx, lds_n_idx] = val.truncf(dtype_)` into LDS then a straight `C_.vec_store(...)` to global memory — no read-add-store, so passing `weight.grad` as `out` today would silently *overwrite* it, not accumulate — this is the concrete gap this plan closes; naively wiring `out=weight.grad` without the kernel-level `accumulate` flag would be a correctness bug, not a perf optimization.

## Phase 1: Add `accumulate: bool` to `gemm_tn`'s epilogue

**Files:** `quack/amd/gemm_gfx950_tn.py`

**Approach:** Thread a compile-time `accumulate: bool` parameter through `_compile_tn_kernel` (`gemm_gfx950_tn.py:76-...`) down to the writeback loop (`gemm_gfx950_tn.py:527-548`). When `accumulate=True`, each output vector store becomes a load-add-store: read the existing `out[m_global, n_offset+...]` value (same dtype as `out`, so no cast round-trip needed beyond what the kernel already does for the non-accumulate store), add the freshly computed `val.truncf(dtype_)` result, store the sum. This is a compile-time flag (baked into the kernel symbol name, like the existing `dtype_str`/`M`/`N`/`K`/tile-shape specialization keys, `gemm_gfx950_tn.py:680-686`), not a runtime branch — no AST-rewriter interaction needed (this sidesteps G4's entire "is this a compile-time or dynamic condition" question by construction, since `accumulate` is a Python `bool` known when the kernel is built, exactly like `has_bias`/`activation` are in the other GEMM kernels surveyed for G4). Extend `_gemm_tn_out`'s custom-op wrapper and `gemm_tn`'s public signature with the same flag, defaulting to `False` (preserving today's overwrite behavior for every existing caller).

**Risks:** The load-add-store changes the writeback's memory traffic pattern (an extra global load per output element) — for the *fused-grad-accum* use case this is still a net win versus materializing a whole separate `dweight` tensor and doing a second full-tensor pass to add it in, but it does make the TN kernel itself slightly slower in isolation when `accumulate=True`, which is expected and fine, not a regression to chase. Precision: accumulating in the kernel's output dtype (bf16/f16, per `gemm_gfx950_tn.py:678`'s `a.dtype == b.dtype == out.dtype` assertion) risks compounding rounding error over many accumulation steps more than autograd's own add would (autograd's add is *also* in the grad's dtype today, so this is not a new precision regression versus current AMD behavior — but it's worth confirming NVIDIA's `gemm_add_inplace` accumulates in the same dtype as `out` too, so AMD isn't introducing a precision behavior NVIDIA's version doesn't already have. `quack/gemm_interface.py:798`'s docstring `out = alpha * A @ B + beta * out` gives no dtype promotion, consistent with same-dtype accumulation — matches).

**Done criteria:** `gemm_tn(a, b, out=existing_tensor, accumulate=True)` produces `existing_tensor_before + a.T @ b` (verified against a torch reference: `existing.clone() + (a.float().T @ b.float()).to(existing.dtype)`, at the same tolerance the existing `test_gemm_tn.py` uses for the non-accumulate path); `accumulate=False` (or omitted) is bit-identical to today's `gemm_tn` output (regression check — this is a strict superset of existing behavior, not a replacement).

## Phase 2: Wire `fuse_grad_accum` into `LinearFunc`/`LinearActFunc`

**Files:** `quack/amd/linear.py`

**Approach:** Add `fuse_grad_accum: bool = False` to `LinearFunc.forward`'s signature and `linear_train`'s public signature (mirroring NVIDIA's `quack/linear.py:198-200`'s `linear_func`), analogously for `LinearActFunc`/`linear_act_train`. In `forward`, when `fuse_grad_accum` is set, save the original (pre-`.reshape()`) `weight` tensor on `ctx` (matching NVIDIA's `weight_og` — necessary here too, since AMD's `forward` also reshapes/contiguous-copies `x`/`weight` before use, `linear.py:281-283`, so the object with a real `.grad` attribute must be captured before that). In `backward`, replace the unconditional `dweight = gemm_tn(dout2, x)` (`linear.py:308`, and `linear.py:425` for the activation variant) with: if `fuse_grad_accum` and `weight_og.grad is not None` and not under `torch.compiler.is_compiling()` (same three-way guard NVIDIA uses, `quack/linear.py:53` — `torch.compile` graph-breaks on this pattern for the same reason on both backends: mutating an arbitrary saved tensor's `.grad` inside a traced backward isn't something dynamo handles, so fall back to the plain path when compiling), call `gemm_tn(dout2, x, out=weight_og.grad, accumulate=True)`, set `dweight = weight_og.grad`, then set `weight_og.grad = None` before returning `dweight` — replicating NVIDIA's exact hijack-the-accumulation trick (`quack/linear.py:57-59`) so autograd doesn't double-add. Otherwise (first call, `weight.grad is None`, or shape/dtype outside Phase 1's `gemm_tn` constraints — `K` multiple of 64, `M` multiple of 128, `N` multiple of 256, per `gemm_gfx950_tn.py:704-706`), fall back to today's `dweight = gemm_tn(dout2, x)` unconditionally (the correct-but-unfused path) — do not attempt a bespoke torch `.add_()` fallback for the "kernel doesn't support this shape" case beyond what already happens today, since that's just today's existing behavior, not a new code path to build and test.

**Risks:** In-place `.grad` mutation interacting with autograd is the named risk in the task brief, and it's real: any caller that reads `weight.grad` *between* the fused kernel's accumulate-in-place write and the `weight_og.grad = None` reset (e.g. a custom hook, or a gradient-clipping utility that runs mid-backward via a `register_hook`) would observe a temporarily-stale or temporarily-doubled state depending on exact timing — this is the same risk NVIDIA's implementation already accepts (it is not new to the AMD port), so the mitigation is documentation-parity with NVIDIA's approach, not inventing a safer AMD-only scheme that would diverge in behavior between backends. `weight_og` must be the actual leaf tensor with a `.grad` attribute PyTorch's optimizer will read — confirm this by checking that `nn.Linear`-style callers (`quack/amd/linear.py` doesn't currently define an `nn.Module` wrapper analogous to NVIDIA's `Linear(nn.Linear)` at `quack/linear.py:351-368`; check `quack/amd/linear_training.py` and any AMD `nn.py` for whether one exists or needs the same `fuse_grad_accum` constructor flag) pass the same `weight` object through forward that PyTorch's optimizer later reads `.grad` from, not a copy.

**Done criteria:** A test (new, in `tests/amd/test_linear_train.py`) runs two backward passes through `linear_train`/`LinearFunc` with `fuse_grad_accum=True` and no intervening `optimizer.zero_grad()`, and confirms `weight.grad` after the second backward equals a manual accumulation: run the same two forward/backward passes with `fuse_grad_accum=False`, manually sum the two returned `dweight`s, and compare (at the same dtype-appropriate tolerance `test_linear_train.py` already uses elsewhere) — this is exactly the test the task brief specifies ("grad matches a manual accumulate over 2 backward passes"). A second test confirms `fuse_grad_accum=True` on the *first* backward pass (`weight.grad is None` initially) produces the same result as `fuse_grad_accum=False` (exercises the fallback branch, not just the fused branch).

## Phase 3: Extend to `linear_training.py` if it has an independent grad path

**Files:** `quack/amd/linear_training.py` (conditional on Phase 3's own investigation step below)

**Approach:** `quack/amd/linear_training.py` has its own `forward`/`backward` autograd Functions (`_LinearActTrainFunc`-style classes per the earlier grep, `linear_training.py:134,143,161,184,268,282,451,467`) for activation- and gate-fused training paths, separate from `quack/amd/linear.py`'s `LinearFunc`/`LinearActFunc`. Before extending `fuse_grad_accum` there too, check whether any of `linear_training.py`'s backward passes compute a `dweight` via `gemm_tn` the same way `linear.py`'s do (`grep -n gemm_tn quack/amd/linear_training.py`) — if so, the same Phase 1/2 pattern applies directly (`gemm_tn(..., out=weight_og.grad, accumulate=True)`); if `linear_training.py`'s dweight computation goes through a different kernel entirely (e.g. a fused-dact kernel that produces `dweight` as a side output alongside `dpreact`, which the earlier read suggested might be the case for `_fused_dact_eligible`-gated paths), extending `fuse_grad_accum` there needs that kernel to gain its own `accumulate` flag — a separate, kernel-specific follow-on, not a copy-paste of Phase 1.

**Risks:** Scope creep — `linear_training.py` is materially larger and more varied (568 lines, MLP/gated/dact variants) than `linear.py`; do not expand this phase into "add `fuse_grad_accum` everywhere training-related" without first confirming which of its paths actually share `gemm_tn` as the dweight kernel.

**Done criteria:** either (a) `linear_training.py`'s relevant backward passes gain `fuse_grad_accum` using Phase 1/2's exact mechanism, with the same two-pass-accumulation test pattern, or (b) this phase concludes "out of scope, needs kernel-specific accumulate support in [named kernel]" and is explicitly deferred — either outcome is an acceptable, honest close to this phase; silently skipping the investigation is not.

## Roadmap (explicitly out of scope here)

- **`torch.compile` compatibility for `fuse_grad_accum`** — NVIDIA's own implementation already disables the fused path under `torch.compiler.is_compiling()` (`quack/linear.py:53`); AMD inherits the same limitation by design, not as a gap to close later unless NVIDIA's does too.
- **Fused grad accumulation for `dx`** (the input gradient, `gemm_nn` in `linear.py:301`) — NVIDIA's `fuse_grad_accum` only covers the *weight* gradient (there's no analogous persistent `.grad` buffer for `x`, which isn't a leaf parameter in the normal case), so this AMD port matches that scope, not a superset.
- **A bespoke torch-side `.add_()` fallback for kernel-unsupported shapes** — deliberately not built (Phase 2); the existing "compute fresh `dweight`, let autograd accumulate" path already handles this correctly, just without the fusion win.

## Self-Review

The specified test ("grad matches a manual accumulate over 2 backward passes") is Phase 2's primary done-criterion, stated precisely (compare fused-path `.grad` after two backward calls against a manual sum of two independent `dweight`s from the unfused path). ✓

**Placeholder scan:** Phase 2's autograd hijack (`weight_og.grad = None` after reading it) is explained with the *reason* it's necessary (prevent double-accumulation by PyTorch's own engine), not just copied as a magic line from NVIDIA's code. Phase 3 does not promise to extend `linear_training.py` unconditionally — it specifies the exact grep/investigation step that decides whether Phase 1's mechanism even applies there, and treats "this needs separate kernel-level work" as a valid, explicitly stated outcome rather than silently dropping the phase. ✓

**Risk honesty:** The in-place-`.grad`-mutation risk is stated as *real and inherited from NVIDIA's existing design*, not as a new AMD-specific danger to be uniquely solved here — this avoids two failure modes: overclaiming AMD safety NVIDIA doesn't have, and underclaiming by treating a known, already-accepted tradeoff as a blocking new risk. ✓
