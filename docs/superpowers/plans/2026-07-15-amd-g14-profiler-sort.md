# AMD Trace Profiler + Reusable Sort Subpackage — Implementation Plan (G14)

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development or superpowers:executing-plans. Design-level; expand to TDD tasks before executing.

**Goal:** Two separable, lower-urgency tooling gaps in one plan: (a) give `quack/amd/` an `fx.printf`/LDS-buffer-based intra-kernel Chrome-Trace profiler analogous to NVIDIA's `quack/trace.py`, keyed on an env var, instead of the current one-off hand-instrumented kernels; (b) extract the bitonic sort inlined twice in `quack/amd/topk_kernel.py` and `quack/amd/topk_lds.py` into a reusable `quack/amd/sort/` subpackage that both consume.

**Architecture:** (a) AMD has no device-wide synchronized timer equivalent to NVIDIA's `%globaltimer`; the closest analogue already in use (`gemm_gfx950_nt_4wave_profile.py`) is `llvm.amdgcn.s.memrealtime`, a real-time counter readable via `llvm.call_intrinsic`. The new `quack/amd/trace.py` reuses NVIDIA's two-buffer design (per-slot metadata + ring-buffer events, Chrome Trace JSON output) but swaps `%globaltimer`/`%clock64` for `s_memrealtime` (which is already wall-clock-scaled and cross-CU-comparable, unlike `%clock64`, so the two-timer calibration dance NVIDIA needs may not be required — this is a design question to resolve in Phase 1, not assumed away). (b) The two topk kernels' bitonic compare-swap networks — one single-wave shuffle-based (`topk_kernel.py`), one LDS-based for N>64 (`topk_lds.py`) — share the same stage/sub/`k_outer`/`j` index math but differ in *where the value lives* (register+shuffle vs. LDS). `quack/amd/sort/` factors the shared index-generation math (the compare-swap network shape) into one place, leaving the register-vs-LDS data-movement as a pluggable "backend" each kernel still owns.

**Tech Stack:** New `quack/amd/trace.py`, `quack/amd/sort/__init__.py`, `quack/amd/sort/bitonic.py`. Modify: `quack/amd/topk_kernel.py`, `quack/amd/topk_lds.py`. Read-only references: `quack/trace.py` (NVIDIA), `quack/amd/gemm_gfx950_nt_4wave_profile.py` (existing hand-instrumentation pattern), `tests/amd/test_topk_kernel.py`, `tests/amd/test_topk_lds.py`.

## Background

**Effort L; both sub-projects are tooling, lower urgency than the correctness/perf gaps elsewhere in the port.** This plan is written to be picked up opportunistically, not on a critical path.

### (a) Profiler

`quack/trace.py` (NVIDIA) is a complete, documented intra-kernel Chrome-Trace profiler: `TraceContext` (device-side, `trace.py:267-411`) records 8-byte begin/end/mark events into a per-warp ring buffer in a contiguous GMEM slab, gated by `QUACK_TRACE=1` so disabled runs emit zero profiling code (`trace.py:160-162`); `TraceSession` (host-side, `trace.py:491-552`) allocates the slab, and `write_trace` (`trace.py:609-711`) reconstructs absolute nanosecond timestamps and emits Chrome Trace JSON plus a percentile-histogram summary JSON. Its central design problem — device timers aren't directly nanosecond-comparable across SMs — is solved by reading two clocks (`%globaltimer`, device-wide but coarse-grained; `%clock64`, per-SM, fine-grained but unsynchronized) at init and flush, then linearly calibrating `%clock64` deltas onto the `%globaltimer` timeline (`trace.py:12-25`).

AMD has no direct `quack/amd/trace.py`. The only existing intra-kernel timing in the port is bespoke and narrow: `gemm_gfx950_nt_4wave_profile.py` reads `llvm.amdgcn.s.memrealtime` via `llvm.call_intrinsic(T.i64, "llvm.amdgcn.s.memrealtime", [], [], [])` (`gemm_gfx950_nt_4wave_profile.py:607-610`) at five fixed points in the main loop, threads the five `i64` timestamps through the `scf.for` loop-carry state (`gemm_gfx950_nt_4wave_profile.py:612-678`), and writes only the *last* iteration's five values to a `(NUM_WGS, 5)` output tensor at loop exit (`gemm_gfx950_nt_4wave_profile.py:700-713`) — good enough for "where does one steady-state iteration spend its cycles" on one hand-picked kernel, but not reusable, not multi-event, and not a trace format any viewer understands.

`s_memrealtime` is documented (AMDGPU ISA references, and consistent with why the existing profile kernel uses it for cross-cluster-boundary deltas within one WG) as a wall-clock real-time counter, typically running off a fixed reference clock shared across the whole device rather than per-CU — i.e. it may already be the AMD analogue of NVIDIA's `%globaltimer` (device-wide, coarse-ish resolution) with no `%clock64`-style per-CU fast counter needed for calibration. This needs to be confirmed (or refuted) empirically in Phase 1 rather than assumed, since if true it significantly simplifies the AMD profiler versus NVIDIA's two-timer design.

### (b) Sort

`quack/amd/topk_kernel.py`'s `_build_topk_single_wave_f32` (N ≤ 64, one wave, values live in registers, cross-lane exchange via `shuffle_xor`) and `quack/amd/topk_lds.py`'s `_build_topk_lds_f32` (N up to 4096, one workgroup, values live in LDS, cross-thread exchange via load/store) both implement the identical bitonic network shape: for `stage in range(log2(N))`, for `sub in range(stage+1)`, compute `k_outer = 1 << (stage+1)` and `j = k_outer >> (sub+1)`, then compare-and-conditionally-swap the pair at distance `j` according to the `(idx & k_outer) == 0` ascending/descending rule. Compare `topk_kernel.py:110-135` (shuffle-based) against `topk_lds.py:136-171` (LDS-based `_compare_swap` closure) — the `k_outer`/`j`/`ascending` math is textually near-identical; only the load/store/compare primitive differs (`shuffle_xor` + register compare vs. `SmemPtr.load`/`.store` + `_scf_if`-guarded closure). Both files also duplicate the top-k tail extraction (`out_pos = (N-1) - lane`, descending write) and the not-yet-supported-dtype/shape assertions.

## Phase 1: `s_memrealtime` calibration question + `quack/amd/trace.py` skeleton

**Files:** new `quack/amd/trace.py`

**Approach:** Before porting NVIDIA's two-timer design wholesale, spend this phase resolving whether AMD needs it at all. Write a minimal throwaway kernel (not committed, or committed under `tests/amd/` as a diagnostic, agent's judgment) that launches across enough CUs to span the whole device, has every WG read `s_memrealtime` once at kernel entry and once after a fixed-cycle busy-wait, and writes both values out. Compare spread across WGs/CUs at entry (should be near-zero if it's device-synchronized like `%globaltimer`) and the measured busy-wait delta's implied clock frequency across WGs (should be consistent if it's a fixed reference clock, not a per-CU variable one). If confirmed device-wide and roughly-constant-frequency, `quack/amd/trace.py` can skip NVIDIA's calibration ratio entirely and treat `s_memrealtime` ticks as directly convertible to nanoseconds via one global scale factor (documented from the ISA, or empirically measured once) — a real simplification worth taking. If not confirmed, fall back to NVIDIA's two-timer calibration design, substituting `s_memrealtime` for `%globaltimer` and reusing `%clock64`'s AMD analogue (need to identify the right `llvm.amdgcn.*` intrinsic for a fast per-CU counter, if one exists and is exposed through FlyDSL's `llvm.call_intrinsic` path the same way `s_memrealtime` already is). Once resolved, build `TraceContext`/`TraceSession` mirroring `quack/trace.py`'s structure (module docstring's stated design decisions carry over conceptually: compact 8-byte events, warp-sampling predication, auto-interned region names, Chrome Trace JSON + summary output) but with AMD's event-store primitive (`fx.printf`-adjacent store idiom or a raw LDS/GMEM `store` via FlyDSL, matching how `gemm_gfx950_nt_4wave_profile.py` already writes per-WG results through a `GTensor`/`vec_store` idiom rather than NVIDIA's `cute.arch.store`-with-cache-hint). Gate everything on a `QUACK_AMD_TRACE` env var (distinct name from NVIDIA's `QUACK_TRACE`, since the two backends may run in the same process during comparative benchmarking and must not share a toggle).

**Risks:** The device-timer synchronization question in this phase is the crux of the whole profiler's accuracy — if wrong, all AMD traces would report plausible-looking but incorrect cross-WG timing skew. Treat the calibration experiment's result as a load-bearing finding to document in the module docstring (mirroring how NVIDIA's `trace.py:12-25` documents its own empirical finding about `%clock64` cross-SM spread), not a one-line assumption.

**Done criteria:** the calibration experiment's result (device-synchronized-and-fixed-frequency, or not) is written down in `quack/amd/trace.py`'s module docstring with the measured numbers, mirroring the rigor of `quack/trace.py:15-17`'s own empirical claim about `%clock64`. `TraceContext.create`/`.b`/`.e`/`.flush` and `TraceSession`/`write_trace` exist with the same public shape as NVIDIA's (for muscle-memory parity for anyone who's used the NVIDIA version), gated by `QUACK_AMD_TRACE`, and with `QUACK_AMD_TRACE` unset, compiling any kernel that calls into `TraceContext` emits no extra device code (verified by an IR dump diff, traced-vs-untraced, showing byte-identical or trivially-metadata-different output).

## Phase 2: Migrate `gemm_gfx950_nt_4wave_profile.py` onto the new profiler (proof-of-use)

**Files:** `quack/amd/gemm_gfx950_nt_4wave_profile.py` (or a new sibling file if the migration would otherwise destroy the existing narrowly-scoped kernel that other work may depend on — check for importers first)

**Approach:** `gemm_gfx950_nt_4wave_profile.py`'s five fixed timestamp points (`now()` calls at `gemm_gfx950_nt_4wave_profile.py:626,648,654,665,671`) map directly onto five `ctx.b("c0")`/`ctx.e("c0")`-style region markers around the same four MFMA "quadrant" clusters it already delineates in comments (`gemm_gfx950_nt_4wave_profile.py:597-605`). Migrating this one real kernel onto `quack/amd/trace.py` is both the integration test for Phase 1's design and a concrete win (multi-event, multi-iteration Chrome trace instead of last-iteration-only five numbers). Confirm first whether anything imports `gemm_nt_4wave_profile` from outside this file/its own tests (`grep -rn gemm_nt_4wave_profile quack/ tests/`) before deciding to replace vs. duplicate.

**Risks:** the existing kernel's timestamps are captured *inside* an `scf.for` loop-carry (`gemm_gfx950_nt_4wave_profile.py:619-678`) specifically because DSL loop-carried state was the only way to get a value out of the loop's last iteration; `TraceContext`'s per-event store-to-GMEM approach sidesteps that entirely (every iteration's events are stored immediately, not carried), which should simplify this kernel's loop state (fewer carried values) as a side benefit — but confirm removing the ts0..ts4 loop-carry slots doesn't change the compiler's register allocation enough to alter the perf numbers being measured (a profiler that perturbs the thing it's measuring is a known hazard called out implicitly by NVIDIA's own "minimal live registers" design goal, `trace.py:35-42`).

**Done criteria:** the migrated kernel produces a valid Chrome Trace JSON (loadable in `chrome://tracing` or Perfetto — verify by loading the schema, not just "no exception") showing the four quadrant clusters as named regions across multiple main-loop iterations, not just the last one; a before/after perf comparison (this box has gfx950 hardware, so this *can* be executed and measured, unlike Plan G12) confirms the new instrumentation doesn't regress the kernel's steady-state throughput outside noise, or if it does, that regression is documented rather than silently accepted.

## Phase 3: Extract `quack/amd/sort/bitonic.py`

**Files:** new `quack/amd/sort/__init__.py`, new `quack/amd/sort/bitonic.py`; modify `quack/amd/topk_kernel.py`, `quack/amd/topk_lds.py`

**Approach:** Factor the shared bitonic-network index math — the `(stage, sub) → (k_outer, j, ascending_predicate)` generation, currently textually duplicated at `topk_kernel.py:110-113,121-126` and `topk_lds.py:136-139,155` — into a small pure-Python (compile-time, not DSL) generator in `bitonic.py`, e.g. `bitonic_network(log2_n: int) -> Iterator[tuple[int, int, ...]]` yielding `(k_outer, j)` pairs (or whatever shape both call sites actually need — confirm by diffing the two call sites exactly before designing the generator's signature, since `topk_kernel.py` needs a `direction_ascending` *predicate expression* built from `tid`/`k_outer` while `topk_lds.py` needs it built from `p0`/`k_outer` — the ascending/descending *rule* is shared, but which DSL value it's applied to is backend-specific, so the generator should yield the (k_outer, j) integers and let each call site build its own predicate). Keep the register-shuffle backend (`topk_kernel.py`'s `shuffle_xor` + select) and the LDS backend (`topk_lds.py`'s load/store + `_scf_if`) as they are — do not force them through one polymorphic "backend" abstraction unless the two call sites turn out to need genuinely identical code around the network, which is unlikely given one operates per-lane-in-registers and the other per-thread-via-LDS-addresses. If a natural shared piece beyond the index math emerges during the diff (e.g. the descending top-k tail-extraction position math, `topk_kernel.py:137-149` vs. `topk_lds.py:173-187`, which do look closer to literally shared), factor that too, but only after confirming the two are computing the same thing under different variable names, not coincidentally-similar-looking different things.

**Risks:** Over-abstracting a "sorting network generator" for a use case with exactly two call sites is exactly the kind of speculative generality QuACK's engineering culture pushes back on (see the project's general preference for concise, self-explanatory code over premature abstraction) — keep `bitonic.py`'s surface area to what these two kernels' current code literally duplicates, not a general-purpose sort library. If the shared surface turns out to be small (just the `(k_outer, j)` sequence, a five-line nested loop), that's fine — a small honest extraction beats a large speculative one.

**Done criteria:** `tests/amd/test_topk_kernel.py` and `tests/amd/test_topk_lds.py` pass unchanged after both kernels are rewired onto `quack/amd/sort/bitonic.py`'s shared network generator (regression, not new behavior); the two kernel files' line count each drops by roughly the size of the duplicated block; `quack/amd/sort/bitonic.py` has no dependency on either `topk_kernel.py` or `topk_lds.py` (one-directional: sort → topk, not the reverse), confirmed by `grep -n "^from\|^import" quack/amd/sort/bitonic.py` showing no `quack.amd.topk*` imports.

## Roadmap (explicitly out of scope here)

- **Multi-wave (N > 64) bitonic *merge* across waves for `topk_kernel.py`** — the file's own docstring already flags this as a follow-up (`topk_kernel.py:18-20`); unrelated to this plan's extraction goal and not attempted.
- **A general-purpose sorting-network code generator** (bitonic merge networks, odd-even mergesort, etc. beyond what topk needs) — deliberately not built; see Phase 3 risk note on over-abstraction.
- **Wiring `QUACK_AMD_TRACE` profiling into the autotuner** (`quack/amd/_gemm_tune.py`) for automatic regression detection — a plausible future use of Phase 1's profiler, not part of this plan.
