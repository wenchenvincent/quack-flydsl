# Composable Epilogue Framework — Implementation Plan (G4)

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development or superpowers:executing-plans. Design-level; expand to TDD tasks before executing.

**Goal:** Turn `quack/amd/epi_ops.py` + `gemm_default_epi.py` from unused scaffold into a real, `begin`/`loop`/`end`-lifecycle `EpiOp` framework that at least one AMD kernel actually calls, migrating that kernel's hand-rolled inline epilogue onto it as proof before considering wider adoption.

**Architecture:** NVIDIA's `quack/epi_composable.py` + `quack/epi_ops.py` compose a tuple of `EpiOp` descriptors into a mixin (`ComposableEpiMixin`) that auto-generates smem sizing, TMA-atom collection, and the three epilogue lifecycle hooks (`epi_begin`, `epi_begin_loop`, `epi_end`) a CUTLASS-style *class-based* kernel invokes at fixed points. AMD's kernels are not class-based — each is one `@flyc.kernel` function with the epilogue math inlined directly into the per-lane writeback loop (`gemm_gfx950.py`, `gemm_norm_act_kernel.py`, `gemm_gated.py` all do this independently, each re-deriving the same alpha/beta/bias/activation sequencing). `quack/amd/epi_ops.py`'s own docstring already states the plan's shape: "a strict subset... we drop the per-stage smem allocation and the begin/begin_loop/end lifecycle hooks... When an epilogue grows to need LDS scratch, extend `EpiOp` with the lifecycle methods." This plan is that extension, but scoped to what a **function-based** `@flyc.kernel` body can call — not a mixin on a class that doesn't exist in this codebase's kernel style — and validated end-to-end on exactly one kernel before any second migration is attempted.

**Tech Stack:** `quack/amd/epi_ops.py`, `quack/amd/gemm_default_epi.py`, `quack/amd/gemm_gfx950.py` (migration target), `quack/amd/gemm_norm_act_kernel.py`, `quack/amd/gemm_gated.py` (read for epilogue-shape survey only, not migrated in this plan). NVIDIA references: `quack/epi_composable.py`, `quack/epi_ops.py`.

## Background — why this is high risk, stated up front

`quack/amd/epi_ops.py` and `quack/amd/gemm_default_epi.py` exist (`epi_ops.py`, 62 lines; `gemm_default_epi.py`, 65 lines) but nothing in `quack/amd/` imports them (`grep -rln "from quack.amd.epi_ops\|from quack.amd.gemm_default_epi" quack/amd/*.py` returns nothing beyond the files themselves). Every AMD kernel with an epilogue re-derives it inline:

- `gemm_gfx950.py`'s `_build_gemm_16x16` (via its `apply_epilogue`-shaped inline block, `gemm_gfx950.py:231-283`) sequences bias load → alpha scale → beta·C add → bias add → activation (relu/relu_sq/gelu_tanh_approx/silu, `gemm_gfx950.py:262-283`), specialized per `(has_bias, activation, has_alpha, has_c)` combination via the symbol-name suffix scheme (`gemm_gfx950.py:83-84`).
- `gemm_norm_act_kernel.py` sequences bias → colvec×rowvec → activation (`gemm_norm_act_kernel.py:178-208`) — a *different* op ordering than `gemm_gfx950.py` (norm-scale before activation, no beta/alpha/C term at all).
- `gemm_gated.py` computes two parallel accumulators (gate, up) and combines them via a *gate function* (`_apply_gate`, `gemm_gated.py:55-81`) — an epilogue shape neither of the other two kernels has (two accumulators in, one combine-op out, no bias/alpha/beta path).

These three are not three specializations of one general epilogue — they are three different epilogue *shapes* (linear chain of scalar terms; linear chain with a different term set and no C/alpha/beta; two-accumulator combine). A composable framework that only accommodates the first shape would not actually replace the other two; forcing all three through one `EpiOp` tuple protocol risks the worst outcome for this kind of refactor — a framework that's more code than what it replaces, with escape hatches everywhere, that nobody then uses for new kernels (which is exactly the current state of the *existing* unused scaffold). This plan's central discipline: build the framework driven by **one** real migration target (`gemm_gfx950.py`, since it's the most general of the three — bias + alpha + beta·C + activation), prove it there, and explicitly leave `gemm_norm_act_kernel.py`/`gemm_gated.py` as future migrations rather than promising all three now.

**The AST-rewriter constraint (per this repo's own port-conventions) is the other reason this is high risk.** Per `AGENTS.md`'s AMD-port section: `@flyc.kernel` bodies are AST-rewritten (`if` → `scf.if`, `for` over a dynamic bound → `scf.for`); **external helpers must call `ReplaceIfWithDispatch.scf_if_dispatch` explicitly** — the rewriter only operates on code lexically inside the `@flyc.kernel` function body. This directly constrains what an `EpiOp.begin`/`.loop`/`.end` lifecycle hook can look like on AMD: if any hook needs a *dynamic* (`fx.const_expr`-only, i.e. compile-time, conditions are fine; runtime-value conditions are not) `if`, and that hook is a plain external function/method called from inside the kernel body (as NVIDIA's `epi_composable.py:114-157`'s `epi_begin` is, being `@cute.jit`-decorated but *not* textually inside the kernel), the AMD version cannot rely on the same trick — it must either (a) restrict every `EpiOp` hook to compile-time-only branching (`fx.const_expr(...)`, which is what every current inline epilogue already does — `gemm_gfx950.py:234,236,238,249...` are all `fx.const_expr` guards, not dynamic ones), sidestepping the constraint entirely because there's no dynamic control flow in an epilogue that only depends on which optional tensors were passed, or (b) have hooks needing genuine dynamic branching call `ReplaceIfWithDispatch.scf_if_dispatch` explicitly, mirroring the existing pattern in `gemm_streamk.py:44-47` and `topk_lds.py:38-43`. Phase 1 must decide which applies **before** designing the hook signatures, not discover it mid-port.

## Phase 1: Survey + decide the hook shape (design-only, no code)

**Files:** none modified; this phase's output is a short design note (can live as an expanded comment block at the top of `quack/amd/epi_ops.py` once Phase 2 starts, or as this plan's own addendum)

**Approach:** Enumerate, precisely, every distinct epilogue term across the three reference kernels (`gemm_gfx950.py`, `gemm_norm_act_kernel.py`, `gemm_gated.py`) and classify each as compile-time-conditional-only (the common case — "is bias present" is a Python `bool` known at kernel-build time, not a runtime value) vs. needing a genuinely dynamic (`scf.if`) branch. Based on the Background section's reading, expect **all** current epilogue branching to be compile-time (`fx.const_expr`) — confirm this by grep (`grep -n "fx.const_expr\|arith.cmpi" quack/amd/gemm_gfx950.py quack/amd/gemm_norm_act_kernel.py quack/amd/gemm_gated.py` restricted to the epilogue line ranges cited above) rather than assuming it. If confirmed, the hook-shape decision is easy: `EpiOp.apply(...)` hooks can be plain Python functions called from inside the kernel body (not needing `scf_if_dispatch` at all, since they only ever branch on `fx.const_expr` predicates, which the AST rewriter already leaves alone — per `AGENTS.md`, the rewriter only intercepts `if` on dynamic values). If any epilogue term turns out to need a dynamic branch (e.g. a future stochastic-rounding epilogue keyed on a runtime seed comparison), design that op's hook to call `ReplaceIfWithDispatch.scf_if_dispatch` explicitly and document why, rather than silently writing an `if` that the rewriter would either mishandle or (per the AGENTS.md warning about `arith.andi` guards) silently let all lanes through.

**Risks:** Getting this wrong (assuming compile-time-only when a future op needs dynamic branching) would surface as a correctness bug only when someone adds that future op, not immediately — so this phase's survey needs to be genuinely exhaustive over the *current* three kernels, and the framework's docstring must state the compile-time-only assumption explicitly so a future author adding a dynamic-branching op knows to reach for `scf_if_dispatch` rather than getting silently-wrong lane behavior.

**Done criteria:** a written classification of every epilogue term in all three reference kernels (bias, alpha, beta·C, relu/relu_sq/gelu_tanh_approx/silu activation, colvec, rowvec, gate-combine) as compile-time-only, with citations; the hook-shape decision (plain functions vs. `scf_if_dispatch`-wrapped) stated and justified from that classification, not assumed.

## Phase 2: Extend `EpiOp` with `begin`/`loop`/`end`, keep it function-callable

**Files:** `quack/amd/epi_ops.py`

**Approach:** Extend the existing `EpiOp` dataclass hierarchy (`Scalar`, `RowVecLoad`, `ColVecLoad` — `epi_ops.py:21-62`) with the lifecycle methods the module's own docstring already promised: `begin(self, ...)` (one-time per-tile setup — e.g. loading a bias/colvec/rowvec value once per output lane, matching what `gemm_gfx950.py:234-238` already does *before* the epilogue's per-lane inner loop), and `apply(self, acc, ctx)` (the per-value combine step, matching `gemm_default_epi.py:35-62`'s existing `apply_default_epi` free function — which this phase should absorb into the `EpiOp` protocol rather than leave as a separate parallel path). Skip `end` unless Phase 1's survey found a term needing post-loop cleanup (none of the three reference kernels' epilogues do any accumulation or store beyond the per-lane writeback itself, so `end` may legitimately be a no-op default for now — don't invent work for it). Since Phase 1 is expected to conclude every current hook is compile-time-branch-only, these methods can be ordinary Python methods called directly from inside a `@flyc.kernel` body — no dispatch machinery needed, keeping this simpler than NVIDIA's `@cute.jit`-decorated hooks. `RowVecLoad`/`ColVecLoad` need an actual `begin` implementation now (currently they're descriptor-only, `epi_ops.py:40-59`, with no code that loads anything — the load logic lives inline in each kernel instead, e.g. `gemm_gfx950.py:234-235`'s `bias_val = ArithValue(_load_f_scalar(bias_div, n_base + lane_row))`); extracting that into `RowVecLoad.begin` is the actual point of this phase, not a re-statement of the dataclass fields that already exist.

**Risks:** The load-address arithmetic (`n_base + lane_row`, `out_col`, etc.) differs per kernel's tiling scheme — `RowVecLoad.begin` cannot hardcode an address formula; it must take the lane's output-column index as a parameter supplied by the calling kernel (an `EpiContext`-shaped bundle, mirroring NVIDIA's `EpiContext` in `quack/epi_ops.py:28`, scoped down to whatever an AMD per-lane epilogue actually needs: current accumulator value, output row/col indices, and the tensor/buffer handles for any loadable term). Getting this bundle's shape wrong (too kernel-specific, or too generic to be useful) is the main design risk of this phase — resolve it by designing `EpiContext` against `gemm_gfx950.py`'s actual call site (Phase 3) rather than in the abstract.

**Done criteria:** `EpiOp` subclasses have working `begin`/`apply` implementations that, called standalone (a throwaway script constructing an `EpiContext` and calling `RowVecLoad("bias").begin(...)` etc. outside a real kernel, if FlyDSL's DSL machinery allows that — otherwise deferred to Phase 3's integration test) produce the same address/value expressions the inline code in `gemm_gfx950.py:234-238` currently produces by hand.

## Phase 3: Migrate `gemm_gfx950.py`'s epilogue onto `EpiOp` (the proof)

**Files:** `quack/amd/gemm_gfx950.py`, `quack/amd/gemm_default_epi.py`

**Approach:** Replace `gemm_gfx950.py`'s inline epilogue block (`gemm_gfx950.py:231-283`) with calls into `DEFAULT_EPI_OPS` (`gemm_default_epi.py:26-32`, extended per Phase 2) iterated at kernel-build time (`for op in cutlass.range_constexpr(...)`-style, or a plain Python `for op in DEFAULT_EPI_OPS:` loop unrolled at trace time, matching how the kernel already iterates other compile-time-known tuples). Keep every one of `gemm_gfx950.py`'s existing specializations working — same `(has_bias, activation, has_alpha, has_c)` symbol-name suffix scheme (`gemm_gfx950.py:83-84`), same numerical output — this migration must be behavior-preserving, not a chance to also change what the kernel supports. Do **not** touch `gemm_norm_act_kernel.py` or `gemm_gated.py` in this phase — their different epilogue shapes (Background section) are explicitly future work, listed in the roadmap below, once `gemm_gfx950.py`'s migration has actually shipped and been exercised.

**Risks:** This is the highest-risk phase because it touches a kernel with existing test coverage and real callers (`quack/amd/gemm.py` and `quack/amd/linear.py` both route through `gemm_gfx950.py`'s epilogue-capable variant per `linear.py:83-85`'s fallback path) — a regression here is not confined to unused scaffold, unlike Phases 1-2. Mitigate by doing the migration as a strict framework-in/inline-out swap validated against the *existing* test suite before any cleanup, and by keeping the pre-migration inline code available in git history (not force-deleting the old block in the same commit as introducing the new one, so a revert is a single clean git revert if the migration regresses something the test suite didn't happen to cover).

**Done criteria:** `tests/amd/test_gemm.py` and any `gemm_gfx950`-specific epilogue tests (`grep -rln "gemm_gfx950\b" tests/amd/*.py`) pass unchanged, covering at minimum every `(has_bias, activation, has_alpha, has_c)` combination the current test parametrization already exercises — this is the regression bar, not a lowered one. `gemm_gfx950.py`'s epilogue block is now `DEFAULT_EPI_OPS`-driven with no leftover inline duplicate of the same math (i.e., this is a real replacement, not an addition alongside the old code).

## Roadmap (explicitly out of scope here)

- **Migrating `gemm_norm_act_kernel.py`** onto `EpiOp` — different term set (colvec/rowvec, no alpha/beta/C), a plausible second `EpiOp` subclass (`ColRowVecScale`?) once Phase 3 has proven the framework on one kernel. Not attempted here.
- **Migrating `gemm_gated.py`** — a fundamentally different epilogue *shape* (two-accumulator combine, not a linear term chain); may need a different lifecycle hook entirely (`combine(acc_a, acc_b)` rather than `apply(acc)`), which is enough of a design question to warrant its own follow-on plan rather than folding it into this one's Phase 2 hook design under time pressure.
- **Per-stage smem allocation for LDS-backed epilogue terms** (e.g. a future CShuffle epilogue) — `epi_ops.py`'s docstring already flags this as the trigger for extending `EpiOp` further; no current kernel needs it, so it's not designed here either.
