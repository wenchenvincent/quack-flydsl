# In-Kernel Dynamic Tile Scheduler — Implementation Plan (G13)

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development or superpowers:executing-plans. Design-level; expand to TDD tasks before executing.

**Goal:** Turn `quack/amd/tile_scheduler.py`'s host-side-only scheduling helpers into a reusable in-kernel scheduler — extracting the atomic-work-counter loop that `gemm_streamk.py` already hand-rolls into shared code other persistent kernels can call, plus an in-kernel rasterization/swizzle helper — so future persistent kernels stop re-deriving this mechanics from scratch.

**Architecture:** `tile_scheduler.py` currently answers "what grid size, what mode" (`grid_for_persistent`, `PersistenceMode`, `TilePlan`) but the two device-side loop shapes it documents — STATIC's compile-time strided loop and DYNAMIC's atomic work-counter loop — are each implemented independently inline, once in `gemm_persistent.py` and once (with the atomic mechanics) in `gemm_streamk.py`. This plan factors the DYNAMIC atomic-counter mechanics (llvm.ptr extraction, f32 atomic-fadd, LDS broadcast, barrier, fptosi) out of `gemm_streamk.py` into a small reusable helper in `tile_scheduler.py`, adds an in-kernel tile-index → (bid_m, bid_n) rasterization helper (the in-kernel counterpart of the already-existing host-side `tile_to_mn`/`resolve_raster_order`), and re-wires `gemm_persistent.py` and `gemm_streamk.py` onto the shared helpers as a pure-refactor regression test that the extraction didn't change behavior.

**Tech Stack:** `quack/amd/tile_scheduler.py`, `quack/amd/gemm_persistent.py`, `quack/amd/gemm_streamk.py`, `quack/amd/gemm_streamk_prod.py` (Session A, migrate-second target), `tests/amd/test_tile_scheduler.py`, `tests/amd/test_gemm_persistent.py`, `tests/amd/test_gemm_streamk.py`. NVIDIA reference: `quack/tile_scheduler.py` (`TileScheduler`, `PersistenceMode`, CLC path).

## Background

`quack/amd/tile_scheduler.py` is explicit about its own gap in its module docstring (`tile_scheduler.py:10-14`): "the in-kernel atomic work-counter loop is documented below but not yet emitted; wire it into a client kernel when the perf gain vs. one-wg-per-tile is motivated by profiling." That profiling motivation already exists — `gemm_streamk.py` independently implements exactly this loop (`gemm_streamk.py:82-214`) without importing anything from `tile_scheduler.py` beyond `get_num_cus` (`gemm_streamk.py:42`). `gemm_persistent.py` similarly hand-rolls the STATIC strided loop (`gemm_persistent.py:91-96`) using only `get_num_cus`. Neither kernel uses `PersistenceMode`, `TilePlan`, or `grid_for_persistent` for anything beyond grid sizing at the host boundary — all in-kernel tile-index bookkeeping is duplicated, inline, per kernel.

`gemm_config.py` declares a `persistence_mode: PersistenceMode` field on `GemmConfig` (`gemm_config.py:19,61`) that is currently decorative — nothing reads it to select between the STATIC/DYNAMIC in-kernel loop shapes, because there is no shared in-kernel implementation to select between.

**NVIDIA's CLC has no AMD analogue.** `PersistenceMode.CLC` (NVIDIA's cluster-launch-control, hardware tile-stealing pre-gfx1250) is already declared in the AMD enum (`tile_scheduler.py:74`) purely so callers can express the *intent* "steal work dynamically" without the AMD scheduler code needing a third branch; `grid_for_persistent` transparently treats `CLC` as `DYNAMIC` (`tile_scheduler.py:154-158`). This plan does not add a CLC implementation — it stays degraded to DYNAMIC, as already designed. No action item here beyond keeping this behavior and documenting it in the extracted helper's docstring so a future reader doesn't go looking for a missing CLC code path.

The atomic-counter pattern's known reliability caveat is about a *different* atomic use, not this one: `gemm_streamk_prod.py:24` notes "atomic-fadd guarantees aren't reliable for bf16 on CDNA4" — that's about atomically accumulating partial **output** tiles (`C` in f32 via `raw_ptr_buffer_atomic_fadd`) in the K-split stream-K variant, not the f32 work-counter this plan extracts. The counter is always f32 regardless of the GEMM's data dtype, so this caveat doesn't apply to Phase 1; it's called out here only so the plan doesn't accidentally conflate the two atomics while reading `gemm_streamk_prod.py`.

## Phase 1: Extract the DYNAMIC atomic work-counter helper (pure refactor)

**Files:** `quack/amd/tile_scheduler.py` (add the helper), `quack/amd/gemm_streamk.py` (consume it, no behavior change)

**Approach:** `gemm_streamk.py:81-201` implements, inline inside `@flyc.kernel def kernel(...)`, the full DYNAMIC loop: per-wg initial tile = `wg_id`; per-step guard on `current_tile < total_tiles`; MFMA body; then lane 0 does `llvm.AtomicRMWOp(fadd, counter_ptr, 1.0, monotonic)` into an f32 counter, broadcasts the *old* value through one LDS f32 slot (`SmemPtr` at `tile_idx_offset`), and every lane reads it back post-barrier and `fptosi`s it to the next `tile_idx` (`gemm_streamk.py:182-201`). Extract the parts that are pure counter-claiming mechanics — the `counter_ptr` extraction via `_fly_d.extract_aligned_pointer_as_index` (`gemm_streamk.py:96-98`), the LDS broadcast slot allocation and the `_scf_if(tid == 0, _claim_next_tile)` + `gpu.barrier()` + read-back dance (`gemm_streamk.py:187-201`) — into a function in `tile_scheduler.py`, e.g. `emit_dynamic_next_tile(allocator, tile_idx_offset, counter_ptr, tid)` returning the new `tile_idx` as an `ArithValue`. Leave the *per-tile body* (MFMA, in-range guard, tile decode) as the caller's responsibility — the helper only owns "given the current wg state, claim and return the next tile index," not the GEMM math around it. `gemm_streamk.py` then calls this helper in place of its inline `_claim_next_tile`/broadcast/read-back block; everything else in the kernel (the MFMA body, the `steps_per_wg` compile-time bound, the host-side counter initialization to `num_cus`) is untouched.

**Risks:** Low — this phase is scoped as a literal extraction, not a redesign, specifically so it can be checked as behavior-preserving. The main risk is the `ReplaceIfWithDispatch.scf_if_dispatch` closure-capture subtlety already noted in `gemm_streamk.py:44-47,128-131` (the AST rewriter treats each `if` body as a closure, so `tile_idx` can't be reassigned from inside — the existing code already works around this by computing the next value outside the guard; the extracted helper must preserve that shape, not "clean it up" into a reassignment that would silently break under the rewriter).

**Done criteria:** `tests/amd/test_gemm_streamk.py` passes unchanged after the refactor (same tolerances, same shapes) — this is the regression check that the extraction is behavior-preserving. As an explicit regression-test discipline step: temporarily reverting only the `tile_scheduler.py` helper (leaving `gemm_streamk.py`'s call site in place) should make the test suite fail with an import error, confirming the test actually exercises the new code path rather than silently falling back to old inline logic that was never deleted.

## Phase 2: In-kernel rasterization / swizzle helper

**Files:** `quack/amd/tile_scheduler.py` (add the helper), `quack/amd/gemm_persistent.py` and `quack/amd/gemm_streamk.py` (wire it in, replacing their hardcoded raster order)

**Approach:** Both `gemm_persistent.py:96-97` and `gemm_streamk.py:138-139` decode `tile_idx` into `(bid_m, bid_n)` with a hardcoded `tile_idx // tiles_n, tile_idx % tiles_n` — i.e. always `RasterOrder.AlongN`, with no L2-locality group-swizzle, even though the host-side `tile_scheduler.py` already has `resolve_raster_order`/`tile_to_mn` (`tile_scheduler.py:119-124,161-171`) that pick between `AlongM`/`AlongN` by problem shape and could inform an in-kernel equivalent. Add an in-kernel counterpart — e.g. `tile_idx_to_mn(tile_idx: ArithValue, tiles_m: int, tiles_n: int, raster_order: RasterOrder) -> (ArithValue, ArithValue)` — that mirrors the host-side `tile_to_mn`'s two branches as compile-time-selected `fx.const_expr` arms (raster order is known at kernel-build time, same as today's `tiles_m`/`tiles_n`), so it compiles to the same handful of `//`/`%` ops the kernels already emit, just parameterized instead of hardcoded. A group-swizzle variant (L2-locality grouping, comparable to NVIDIA's `TileScheduler._swizzle_cta` in `quack/tile_scheduler.py:260-286` or the `group_m` swizzle already used in the RDNA reference kernel `FlyDSL/kernels/rdna_f16_gemm.py:129-138`) is a natural follow-on but is scoped as **optional** within this phase — land the plain raster-order parameterization first since it's a strict improvement with zero risk (it's the same math, just not hardcoded), and only add group-swizzle if Phase 2's simple version leaves time, since swizzle correctness is easy to get subtly wrong (off-by-one group boundaries) and this plan has no perf number to justify the complexity yet.

**Risks:** Changing `gemm_persistent.py`/`gemm_streamk.py`'s raster order from the current implicit `AlongN` to a parameterized default must keep `AlongN` as the *default* so this phase, too, stays behavior-preserving unless a caller explicitly asks for `AlongM` or swizzle. Do not change either kernel's default output-tile visitation order as a side effect of this refactor.

**Done criteria:** `tile_idx_to_mn` used by both `gemm_persistent.py` and `gemm_streamk.py` with `raster_order=AlongN` (matching current behavior) reproduces bit-identical results to the pre-refactor hardcoded decode — verified by the same regression tests as Phase 1. If group-swizzle is included, it ships behind an explicit new parameter (not the default) with its own small numerical test (a persistent-kernel run with swizzle enabled matches the same run with swizzle disabled, since swizzle only permutes *which* wg does *which* tile, not the math).

## Phase 3: Migrate a second, independently-authored persistent kernel

**Files:** `quack/amd/gemm_streamk_prod.py` (Session A only — the module explicitly says Session A "matches the semantics of `gemm_f16_persistent` exactly" and exists to validate the runtime `scf.for` loop-carry pattern, `gemm_streamk_prod.py:206-210`)

**Approach:** `gemm_streamk_prod.py` is a large (1775-line) file containing four independent scheduling experiments ("Session A/B/C/D" per its own section comments) exploring runtime-bound loops, K-split shards, and tile-crossing accumulator flush. Only Session A is in scope here — it is structurally the same DYNAMIC/STATIC persistent-loop shape as `gemm_persistent.py`/`gemm_streamk.py`, just with a runtime `scf.for` bound instead of a compile-time `range_constexpr` one (`gemm_streamk_prod.py:113-132`). Migrating Session A onto Phase 1/2's shared helpers is the validation that the extraction generalizes beyond the two kernels used to build it, without taking on Sessions B/C/D's much larger scope (K-split combine, atomic-fadd output accumulation, tile-crossing flush) — those stay hand-rolled; they are solving a materially different problem (partial-tile stream-K) that the shared helper isn't trying to cover.

**Risks:** Session A's runtime `scf.for` loop-carry (`for step, state in range(0, steps_per_wg, init=[zero_i32])`) is a different DSL loop-emission shape than `gemm_streamk.py`'s compile-time `range_constexpr` loop; confirm the Phase 1 helper's signature doesn't assume a `range_constexpr`-only calling context (it shouldn't, since it only touches counter/LDS/barrier state, not the loop shape itself, but this needs to be checked explicitly during migration, not assumed).

**Done criteria:** Session A, after migration, still matches `gemm_f16_persistent`'s output on the same inputs (the property `gemm_streamk_prod.py:208-210` already claims) — add or reuse a test comparing Session A's kernel output against a non-persistent reference `torch.matmul`, run for at least one shape where `total_tiles` isn't a multiple of `num_cus` (to exercise the tail-tile guard).

## Roadmap (explicitly out of scope here)

- **CLC** — stays degraded to DYNAMIC; no AMD hardware analogue exists pre-gfx1250 launch-control equivalents, and none is known to exist on gfx1250 either at time of writing. Not attempted.
- **`gemm_streamk_prod.py` Sessions B/C/D** (K-split shard combine, tile-crossing accumulator flush) — separate, larger scope; not a generalization of this plan's shared helper but a different scheduling problem (splitting one tile's *K*-dimension across workgroups, not just distributing whole tiles).
- **`GemmConfig.persistence_mode` becoming load-bearing** — wiring the config field to actually select STATIC vs. DYNAMIC in-kernel code at kernel-build time is a natural next step once two-plus kernels use the shared helpers, but is separate from *building* the helpers.
