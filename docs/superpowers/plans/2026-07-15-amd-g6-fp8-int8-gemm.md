# Standard fp8/int8/tf32 GEMM (non-blockscaled) — Implementation Plan (Gap G6)

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development or superpowers:executing-plans. Design-level; expand each phase to TDD tasks before executing.

**Goal:** Add plain (unscaled) fp8-e4m3/e5m2 and int8 MFMA GEMM kernels to the AMD FlyDSL port, so `A @ B` in raw fp8/int8 no longer silently falls back to a torch path that itself has no ROCm compute kernel for those dtypes.

**Architecture:** Two new sibling kernel modules mirroring the existing MVP pattern in `quack/amd/gemm_gfx950.py` (`_build_gemm_16x16`): `gemm_gfx950_fp8.py` (fp8 inputs, f32/f16/bf16 accumulate-and-store) and `gemm_gfx950_int8.py` (int8 inputs, i32 accumulate, i32 or dequantized-f32/f16/bf16 store). Both are exposed as new top-level entry points (`gemm_fp8`, `gemm_int8`) alongside — not folded into — the existing `gemm()` dispatcher in `gemm.py`, following the precedent set by `mxfp8_gemm` (a standalone function, not routed through `gemm()`). tf32 gets a design note and an explicit YAGNI deferral rather than an implementation.

**Tech Stack:** `quack/amd/gemm_gfx950.py`, `quack/amd/gemm_gfx950_mfma_core.py`, `quack/amd/gemm.py`, FlyDSL rocdl MFMA wrappers (`flydsl/expr/rocdl/__init__.py`), gfx950 (CDNA4, MI355X) hardware.

## Background the engineer needs

**Current gate.** `quack/amd/gemm.py:67` — `_MFMA_SUPPORTED_DTYPES = {torch.float16, torch.bfloat16}`. `_mfma_eligible()` (`gemm.py:113-141`) and `gemm()` (`gemm.py:151-...`) both check `A.dtype not in _MFMA_SUPPORTED_DTYPES` before dispatching to `_arch_dispatch_mfma()` (`gemm.py:33-46`), so fp8/int8 inputs always fall through to the torch fallback at the bottom of `gemm()` (`out = alpha * (A @ B)`), which raises on ROCm — `torch.mm` has no fp8×fp8 or int8×int8 kernel there. **This is not a port of an existing NVIDIA feature** — `quack/gemm.py` (NVIDIA) has no int8/fp8/tf32 path either; the plain fp8 GEMM here is a new AMD-side addition alongside the already-shipped blockscaled MXFP8 path (`gemm_gfx950_blockscaled.py`).

**The MVP kernel pattern to replicate.** `gemm_gfx950.py:_build_gemm_16x16` (lines 56-299) is a single-workgroup-per-16×16-tile kernel, block=(64,1,1), one wave. Per K-tile of 16 (dtype_str="f16") or — note — the *existing* wrapper classes in `gemm_gfx950_mfma_core.py` already generalize this to K=32 for gfx950 (`_WmmaHalfK32`, lines 84-101). The MVP kernel itself doesn't import those wrapper classes — it inlines the MFMA call directly (`gemm_gfx950.py:220-229`). New fp8/int8 kernels should follow the same inlining style for the MVP (matches precedent) but the fragment-load/epilogue helper functions (`_load_h4`, `_store_out_scalar`, etc., `gemm_gfx950.py:148-184`) are reusable almost verbatim by parameterizing element type/size.

**Intrinsics already available — this significantly de-risks the plan.** Grepping FlyDSL's `flydsl/expr/rocdl/__init__.py` and the upstream MLIR ROCDL dialect (`build-fly/python_packages/flydsl/_mlir/dialects/_rocdl_ops_gen.py`) found:

- `mfma_f32_16x16x32_fp8_fp8` — **already has a Python wrapper** in `flydsl/expr/rocdl/__init__.py:141-144` (used today only by the blockscaled kernel's non-gfx950 branch, `_fly_blockscale_preshuffle_gemm.py:478`). K=32, e4m3×e4m3 → f32 accumulator. Directly usable.
- `mfma_i32_16x16x32_i8` — **already has a Python wrapper**, `rocdl/__init__.py:146-149`. K=32, int8×int8 → **i32** accumulator. Directly usable.
- `mfma_i32_16x16x64_i8` — exists at the raw upstream MLIR level (`_rocdl_ops_gen.py`, confirmed via `dir(rocdl)`) but **has no FlyDSL Python wrapper yet**. This is gfx950's double-rate int8 (K=64). Adding the wrapper is a ~6-line mechanical addition following the exact pattern of `mfma_f32_16x16x32_bf16` (`rocdl/__init__.py:161-165`, which itself is guarded by an `_ods_*` None-check).
- `mfma_f32_16x16x32_bf8_bf8`, `mfma_f32_16x16x32_fp8_bf8`, `mfma_f32_16x16x32_bf8_fp8` — exist upstream (e5m2×e5m2 and the two mixed e4m3/e5m2 combos) but **no FlyDSL wrapper**. Needed only if e5m2 support is in scope (see Phase 3).
- `mfma_f32_16x16x8_xf32` / `mfma_f32_32x32x4_xf32` — exist upstream. This is CDNA's tf32-equivalent (reduced-mantissa fp32 MFMA). No FlyDSL wrapper. See the tf32 note below.

Any new wrapper follows the `_split_mfma_operands` pattern already used for every other MFMA op in that file (`rocdl/__init__.py:75-88` for the operand-splitting helper, then a `@traced_op def mfma_xxx(result_type, operands, *, loc=None, ip=None): ...` body). This is a change to the **FlyDSL repo** (`/workspace/FlyDSL/python/flydsl/expr/rocdl/__init__.py`), which the AMD port already vendors/patches locally per `AGENTS.md`'s reference to `/workspace/FlyDSL` — flag this as a cross-repo dependency, not a `quack/amd/`-only change.

**Fragment sizes (need empirical verification, not just derivation).** By analogy with `_WmmaHalfK32` (K=32, 8 elements/lane, 2-byte f16 → 16 bytes/lane fragment): fp8 K=32 → 8 elements × 1 byte = 8 bytes/lane (fits the existing `BufferCopy64b`/`h4_reg_ty`-style 8-byte vectorized load already used for f16 fragments — same instruction width, different element type). int8 K=32 → same 8 bytes/lane. int8 K=64 (`mfma_i32_16x16x64_i8`) → 16 bytes/lane, needs the `buffer_copy_gmem16_dwordx4`-style 16-byte load already implemented in `_fly_mfma_preshuffle_pipeline.py:482-499` (used by the blockscaled A-load path) rather than a new copy-atom size. **Do not trust this derivation blindly** — `reference_mfma_layouts.md` (project memory) already flags that CDNA MFMA fragment-to-lane mappings must be confirmed empirically (e.g. via `cute.printf`-style dumps comparing kernel output against a hand-computed single-tile case) before building a multi-tile kernel on top of an assumed layout. Phase 0 below is exactly this verification, scoped to fp8/int8 before any tiled kernel is written.

**int8 accumulator/output dtype.** Unlike f16/bf16 (which accumulate in f32 and store f32/f16/bf16), int8×int8 MFMA accumulates in **i32** — there is no implicit dequantization. The MVP should expose `out_dtype=torch.int32` (raw accumulator, exact, trivially testable) as the first correctness milestone. A dequantized f16/bf16/f32 output (`out = (acc.float() * scale_a * scale_b)`) is a natural Phase-2 epilogue extension but is *not* required for G6 to be "done" — the gap catalog only asks for standard int8 GEMM, and raw i32 output already unblocks int8 dot-product use cases (e.g. weight-only quantization dequant done separately, as `mxfp8_ops.py` already does for the fp8 case).

**tf32.** AMD's hardware analog is the CDNA `mfma_f32_16x16x8_xf32`/`mfma_f32_32x32x4_xf32` instructions — genuinely exists, so this is not pure YAGNI on the hardware-availability axis. But there is no `torch` storage dtype "tf32" on ROCm the way NVIDIA's tf32 is a MFMA-internal truncation of a plain `torch.float32` tensor — AMD's xf32 MFMA would work the same way (accept `torch.float32` input, truncate to xf32 precision in hardware during the MFMA). Given (a) no upstream FlyDSL wrapper exists, (b) no test/parity pressure from the NVIDIA side (NVIDIA `quack/gemm.py` has no tf32 path either), and (c) fp8/int8 are the higher-value, more-requested formats per the gap catalog framing ("fp8 first — highest value, int8 second"), this plan explicitly scopes tf32 **out of implementation** and leaves only the design note above. Re-open as its own gap if a workload actually needs it.

## Phase 0 — Investigation: verify fragment layout and intrinsic operand order

**Goal:** confirm (not assume) the per-lane fragment layout for `mfma_f32_16x16x32_fp8_fp8` and `mfma_i32_16x16x32_i8` on gfx950 before writing a tiled kernel around a guess.

- [ ] Write a scratch single-tile kernel (16×16×32, one workgroup, following `_build_gemm_16x16`'s skeleton) that loads a *known* small A/B pattern (e.g. `A[i,k] = i*100+k`, `B[k,j] = 1` for one nonzero k) and dumps the raw per-lane fragment bytes via `cute.printf`-equivalent (`fx.printf`) before the MFMA call, plus the resulting accumulator after. Compare against a hand-computed expected fragment-to-(row,k) and (k,col)-to-lane mapping.
- [ ] Confirm operand order for `rocdl.mfma_f32_16x16x32_fp8_fp8(result_type, [a, b, c, cbsz, abid, blgp])` — verify `cbsz`/`abid`/`blgp` should stay `0` for plain e4m3×e4m3 (mirrors the existing blockscaled kernel's non-gfx950 branch call at `_fly_blockscale_preshuffle_gemm.py:481`, which does exactly this).
- [ ] Confirm `mfma_i32_16x16x32_i8`'s accumulator init is an all-zero **i32x4** vector (not f32x4) — the `acc_ty`/`_zero_list` construction in `_build_gemm_16x16` (`gemm_gfx950.py:186-190`) needs an integer variant (`arith.constant(0, type=T.i32)` instead of `0.0, type=T.f32`).
- [ ] Confirm whether `A.dtype == torch.int8` maps to a signed 8-bit MLIR type directly usable as the MFMA operand element type, or needs an explicit sign-extension/bitcast step before the buffer load (int8 has no "half-precision-style" `T.i8` ambiguity risk the way fp8 e4m3/e5m2 do, but verify the FlyDSL `T.i8`/`T.si8` naming and that `torch.int8` round-trips through `fx.rocdl.make_buffer_tensor` without reinterpretation).

**Done when:** a scratch kernel produces MFMA output matching hand-computed values for both fp8-e4m3 and int8 on a single 16×16×32 tile, with the fragment-to-lane mapping written down (comment block, matching the style of `gemm_gfx950.py`'s own header comment for f16).

## Phase 1 — Design: kernel structure and dispatch surface

- [ ] Decide final module layout: `quack/amd/gemm_gfx950_fp8.py` (new) and `quack/amd/gemm_gfx950_int8.py` (new), each exporting a `_build_gemm_16x16_<family>()` builder + a `torch.library.custom_op`-wrapped launcher + a public `gemm_fp8()` / `gemm_int8()` function — directly mirroring `gemm_gfx950.py`'s `_build_gemm_16x16` / `_gemm_mfma_out` / `gemm_mfma` triad (lines 56-417).
- [ ] fp8 kernel signature: `gemm_fp8(A: Tensor, B: Tensor, *, out_dtype=torch.float32) -> Tensor`, `A`/`B` ∈ `{torch.float8_e4m3fn, torch.float8_e5m2}` (same dtype on both sides for the MVP — mixed e4m3×e5m2 is Phase 3), `out_dtype` ∈ `{f32, f16, bf16}` reusing the existing `_store_out_scalar` downcast helper unmodified.
- [ ] int8 kernel signature: `gemm_int8(A: Tensor, B: Tensor, *, out_dtype=torch.int32) -> Tensor`, `A`/`B` ∈ `{torch.int8}`, `out_dtype` = `torch.int32` only for the MVP (raise `NotImplementedError` for anything else — explicit, not silent).
- [ ] Decide bias/activation/alpha/beta scope for v1: **none** — match the "proof-of-life" framing of the existing `gemm_gfx950.py` MVP (which itself grew bias/activation/alpha/beta as *documented follow-ups*, not day-one). Keep `gemm_fp8`/`gemm_int8` to plain `C = A @ B` for the first landed version; epilogue fusion is a natural Phase-2 for either kernel once the MVP is proven, using `_apply_epilogue` from `gemm_gfx950_mfma_core.py:138-184` (already generic over element type via `out_dtype`/`vec_size` params — should work unmodified for fp8-in/f32-out since the epilogue operates on the *post-MFMA* f32 accumulator, not the input dtype).
- [ ] Decide whether `gemm()` in `gemm.py` should auto-route fp8/int8 calls to the new kernels. **Recommendation: not in this plan.** `_mfma_eligible`'s contract (bias/activation/alpha/beta/C, multiple out_dtypes) doesn't match int8's i32-only output; forcing fp8/int8 through the same eligibility function risks silently wrong dtype coercions (e.g. `effective_out_dtype = out_dtype or A.dtype` at `gemm.py:222` would set `out_dtype=torch.int8` for a bare `gemm(int8_a, int8_b)` call, which is wrong — int8 GEMM output must be i32). Ship `gemm_fp8`/`gemm_int8` as standalone entry points first (matches `mxfp8_gemm` precedent); revisit `gemm()` integration as a follow-up once the shape is proven, with an explicit `out_dtype` requirement for int8 to avoid the silent-coercion trap.

## Phase 2 — Implement: fp8 kernel (highest priority)

**Files:** new `quack/amd/gemm_gfx950_fp8.py`; new `tests/amd/test_gemm_fp8.py`; possibly `flydsl/expr/rocdl/__init__.py` (only if e5m2 is included here — see Phase 3 gate).

- [ ] Port `_build_gemm_16x16`'s structure: same buffer-tensor setup (`fx.rocdl.make_buffer_tensor`), same grid `(M//16, N//16, 1)`, block `(64,1,1)`, but K-tiling in chunks of 32 (`k_tiles = K // 32`) and the fp8 MFMA call (`rocdl.mfma_f32_16x16x32_fp8_fp8`) instead of the f16 one at line 227.
- [ ] A/B fragment loads: reuse `_load_h4`/`_load_h_scalar`-style helpers but parameterized on `elem_bytes=1` (fp8) instead of 2 (f16) — the vec4-unit indexing arithmetic (`vec_idx_A`, `lane_k_base`) changes shape since 8 elements now pack into 8 bytes, not "4 f16 values = 8 bytes." Do not copy-paste blindly; re-derive from the Phase-0 verified fragment layout.
- [ ] Accumulator stays f32x4 (unchanged from f16 kernel) — fp8 MFMA still accumulates in f32.
- [ ] Output store: reuse `_store_out_scalar` unmodified (out_elem_type ∈ {f32,f16,bf16}, same as today).
- [ ] `torch.library.custom_op` registration (`quack_amd::_gemm_fp8_out`) mirroring `_gemm_mfma_out` (`gemm_gfx950.py:327-368`), with `assert A.dtype in (torch.float8_e4m3fn, torch.float8_e5m2)`.
- [ ] Test (`tests/amd/test_gemm_fp8.py`, mirroring `test_gemm_mfma.py`'s structure): reference is `A.float() @ B.float()` — **fp8→f32 upcast is exact** (both e4m3 and e5m2 map exactly into f32's mantissa), so no dequant-scale machinery is needed for correctness, contrary to a first-glance assumption. Parametrize M/N/K ∈ multiples of 16/32, dtype ∈ {e4m3, e5m2} (single-format only — no e4m3×e5m2 mixing in the MVP), out_dtype ∈ {f32, f16, bf16}. Tolerance: fp8 has much larger quantization error than f16 (e4m3 has 3 mantissa bits), so `atol`/`rtol` need to be wider than `test_gemm_mfma.py`'s f16 tolerances — derive from `K * eps(e4m3)^2` similar reasoning, or empirically from the reference run, not copy-pasted.
- [ ] e5m2×e5m2 needs the same `mfma_f32_16x16x32_fp8_fp8`-style call — check in Phase 0 whether the *same* rocdl op handles both formats via `cbsz`/`blgp` operand bits (matching the `mfma_scale_f32_16x16x128_f8f6f4` format-select pattern found in `_fly_blockscale_preshuffle_gemm.py:571-573`, where `cbsz=0`/`blgp=0` selects e4m3) or needs the separate `mfma_f32_16x16x32_bf8_bf8` op (unwrapped — see Background). This determines whether e5m2 is "free" (same kernel, different `cbsz`) or needs a second wrapper + second kernel variant.

**Done when:** `pytest tests/amd/test_gemm_fp8.py -x` passes for e4m3 across several M/N/K/out_dtype combos, values match `A.float() @ B.float()` within a documented (not copy-pasted) tolerance, and disabling the kernel (forcing the torch fallback) makes the test fail with an ROCm-side "no kernel for fp8 matmul" error — confirming the test actually exercises the new path.

## Phase 3 — Implement: int8 kernel

**Files:** new `quack/amd/gemm_gfx950_int8.py`; new `tests/amd/test_gemm_int8.py`.

- [ ] Same structural mirroring as Phase 2, using `rocdl.mfma_i32_16x16x32_i8` (already wrapped).
- [ ] Accumulator: **i32x4**, zero-initialized via `arith.constant(0, type=T.i32)` (not `0.0`/`T.f32` as in the f16/fp8 kernels) — this is the one genuinely different piece of `_build_gemm_16x16`'s skeleton, not just a parameterization.
- [ ] Output store: new integer store path (no `.truncf()` float downcast — output dtype is i32, store raw). Reuse the buffer-copy machinery, not `_apply_epilogue`/`_store_out_scalar` (those are float-typed).
- [ ] `mfma_i32_16x16x64_i8` (K=64, double-rate) is a stretch goal for this phase, not required for "done" — needs the new FlyDSL wrapper (Background) and the 16-byte fragment load pattern. Land the K=32 kernel first; note K=64 as a documented follow-up in the module docstring (matching how `gemm_gfx950.py` documents its own follow-ups).
- [ ] Test: reference via exact-arithmetic accumulation, not a GPU int32 matmul (torch has no reliable int32 GPU matmul on ROCm either). Use `(A.to(torch.float64) @ B.to(torch.float64)).round().to(torch.int32)` — float64's 52-bit mantissa is exact for int8×int8×K sums well beyond any K this MVP will test (int8 range ±127, K up to a few thousand stays within 2^52). Parametrize M/N/K multiples of 16/32.

**Done when:** `pytest tests/amd/test_gemm_int8.py -x` passes with **exact** integer match (no tolerance — int8 MFMA accumulation is exact, unlike float MFMA) against the float64 reference.

## Phase 4 — tf32 (design-only, explicitly deferred)

- [ ] No implementation. Leave a short note in `gemm_gfx950_fp8.py`'s or `gemm.py`'s module docstring pointing at this plan and `mfma_f32_16x16x8_xf32`/`mfma_f32_32x32x4_xf32` as the eventual hardware hook, so a future engineer doesn't have to re-derive intrinsic availability from scratch.
- [ ] Re-open as a separate gap/plan only if a concrete workload asks for it — do not implement speculatively (YAGNI call, per the task's own framing).
