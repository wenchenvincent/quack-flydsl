# GEMM Epilogue Stochastic Rounding — Implementation Plan (Gap G8)

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development or superpowers:executing-plans. Design-level; expand each phase to TDD tasks before executing.

**Goal:** Replace the `sr_seed` placeholder in the AMD GEMM epilogue with real stochastic rounding for the f32→bf16/f16 writeback, wired into one kernel behind a flag.

**Architecture:** gfx950 (CDNA4) has **genuine native hardware support** for this — `v_cvt_sr_pk_bf16_f32`/`v_cvt_sr_pk_f16_f32` (LLVM intrinsics `llvm.amdgcn.cvt.sr.pk.bf16.f32` / `.pk.f16.f32`), gated by the `GFX950Insts` feature bundle. This directly parallels NVIDIA's `cvt.rs.satfinite.bf16x2.f32` used in `quack/rounding.py`, so the AMD design mirrors the NVIDIA one closely: a portable counter-based PRNG (Philox, reimplemented with `arith.mului_extended` instead of NVPTX-specific inline asm) feeds a 32-bit seed per lane-pair into the hardware SR-convert instruction. FlyDSL has no Python wrapper for this instruction yet — that wrapper is this plan's first concrete deliverable, added the same way `cvt_pk_bf16_f32` (round-to-nearest) is already wrapped via `llvm.inline_asm` in `flydsl/expr/rocdl/inline_asm.py`.

**Tech Stack:** `quack/amd/gemm_default_epi.py`, `quack/amd/gemm_gfx950.py` (writeback site), `quack/rounding.py` (NVIDIA reference — Philox, not the PTX-specific SR call), FlyDSL `rocdl/inline_asm.py`, LLVM AMDGPU intrinsics (`llvm.amdgcn.cvt.sr.pk.bf16.f32`), gfx950 hardware.

## Background the engineer needs

**Current state is a real placeholder, confirmed.** `grep`ing the whole `quack/amd/` and `tests/amd/` trees for `sr_seed`/`apply_default_epi`/`DEFAULT_EPI_OPS` finds exactly three hits: the definition site (`gemm_default_epi.py`), and one shape-only test (`tests/amd/test_gemm_config.py:79-82`, `test_default_epi_ops_shape`, which only asserts the *tuple of names* includes `"sr_seed"` — it never rounds anything). No kernel imports `apply_default_epi` or consumes `sr_seed`. `gemm_default_epi.py:12` — `"Stochastic rounding (gfx950 has hardware support; wire via rocdl)."` — and `gemm_default_epi.py:29` — `Scalar("sr_seed", dtype="i32", default=0),` — are exactly the TODO cited in the gap catalog. This plan makes that comment's claim true.

**Phase-1's core question was answered by reading LLVM's own AMDGPU intrinsic definitions (vendored at `/workspace/llvm-project`), not left to a runtime probe — this is the single most load-bearing finding in this plan and changes the shape of the work substantially from a naive "AMD probably has to fake it in software" assumption:**

- `int_amdgcn_cvt_sr_pk_bf16_f32` (`llvm/include/llvm/IR/IntrinsicsAMDGPU.td:593-595`) — `(float src0, float src1, i32 seed) -> v2bf16`. A **packed**, non-tied, pure intrinsic: two f32 values in, one bf16-pair out, stochastically rounded, using one 32-bit seed for the pair. This is the direct AMD analog of NVIDIA's `cvt.rs.satfinite.bf16x2.f32` (`quack/rounding.py:63-88`, `cvt_f32x2_bf16x2_rs`) — same shape (2-in, packed-2-out, one seed).
- `int_amdgcn_cvt_sr_pk_f16_f32` (same file, `:589-591`) — the fp16 sibling.
- `int_amdgcn_cvt_sr_bf16_f32` / `int_amdgcn_cvt_sr_f16_f32` (`:829-830`, via `AMDGPUCvtScaleSRF32ToBF16F16TiedInputIntrinsic`) — a **tied-input, single-lane** variant: `(v2bf16 old_vdst, float src0, i32 seed, i1 dst_lo_hi_sel) -> v2bf16`, writes just one half of the packed destination, preserving the other from `old_vdst`. Useful if writing scalar-at-a-time; not needed if the epilogue is restructured to process f32 accumulator values in pairs (recommended — see Phase 2).
- **Hardware gating, confirmed via `AMDGPU.td`:** `V_CVT_SR_PK_BF16_F32` is defined under `let SubtargetPredicate = HasBF16ConversionInsts` (`VOP3Instructions.td:1762-1765`), and `VOP1Instructions.td:316` shows `HasGFX950Insts` requires `HasBF16ConversionInsts` as an `OtherPredicate` — i.e. **the `GFX950Insts` feature bundle includes `FeatureBF16ConversionInsts`** (`AMDGPU.td:2050`, `2156` — both gfx950-family subtarget definitions list `FeatureBF16ConversionInsts`). Separately, `AMDGPU.td:486-499`'s `GFX950Insts` feature-bundle definition explicitly lists `FeatureF32ToF16BF16ConversionSRInsts` and `FeatureCvtPkF16F32Inst` as included features. **Conclusion: gfx950 (our primary validation target, MI350/MI355X) has this instruction in hardware.** gfx942 (CDNA3) support is not confirmed by this reading and should not be assumed — gate the feature behind an explicit arch check (`quack/amd/flydsl_utils.py:get_rocm_arch`) rather than enabling it unconditionally.

**Consequence for scope:** this plan is **not** "add a software SR fallback" as a first guess might suggest — it's "wrap one missing FlyDSL intrinsic, write a portable PRNG, and wire two things together." The manual add-random-bits-then-truncate software technique is kept only as a documented Phase-0 fallback path in case Phase 0's hardware verification surfaces a gap between the LLVM `.td` definition and what actually assembles/executes on the box (definitions in `.td` files describe what the *backend* can codegen, not a 100% guarantee the *specific ROCm toolchain version* installed exposes it cleanly through inline asm/intrinsic-call — verify before committing to the hardware path as the only implementation).

**No generic LLVM-intrinsic-call mechanism confirmed in FlyDSL** — the existing precedent for "ROCDL op with no MLIR ROCDL-dialect wrapper" is hand-written `llvm.inline_asm` (`flydsl/expr/rocdl/inline_asm.py`, e.g. `cvt_pk_bf16_f32` at line 52-67: emits the literal mnemonic `v_cvt_pk_bf16_f32 $0, $1, $2` with `"=v,v,v"` constraints). Follow this exact pattern for `cvt_sr_pk_bf16_f32` (mnemonic `v_cvt_sr_pk_bf16_f32 $0, $1, $2, $3`, constraints `"=v,v,v,v"` — 2 f32 sources + 1 i32 seed). Inline-asm is more fragile than a real dialect op (no operand-type checking by MLIR, relies on the assembler accepting the literal mnemonic string) but matches the codebase's existing convention exactly, and avoids a much larger yak-shave of adding real ROCDL-dialect tablegen entries (`MmaAtom.td`-style) for a single conversion op.

**Portable PRNG — do not port `quack/rounding.py`'s `mul_wide_u32` verbatim.** `quack/rounding.py:38-59`'s `mul_wide_u32` is implemented via `llvm.inline_asm` emitting literal **PTX** (`mul.wide.u32 prod, $2, $3;`) — this will not assemble on the AMDGPU backend (different ISA entirely). The Philox algorithm itself (`philox()`, `:92-128` — 4×32 counter-based PRNG, `PHILOX_ROUND_A/B`, `PHILOX_KEY_A/B` constants, `n_rounds` unrolled loop of `hi,lo = mul_wide_u32(...)`) is portable; only the "32×32→64-bit widening multiply" primitive needs an AMD-native replacement. **Confirmed available:** `arith.mului_extended` (`arith` dialect, portable across LLVM backends — verified present in FlyDSL's generated MLIR bindings, `build-fly/python_packages/flydsl/_mlir/dialects/_arith_ops_gen.py:2306`, `def mului_extended(lhs, rhs, ...) -> (low, high)`). This is a strictly better building block than the PTX inline-asm version — same semantics, zero backend-specific code, should lower to AMDGPU's native `v_mad_u64_u32`-class widening multiply automatically via LLVM's standard `mulhu`/`umul_with_overflow`-style legalization. Reimplement `philox()` on top of `arith.mului_extended` (same constants, same round structure, same 4-word state) rather than copying the PTX asm wrapper.

**Where to wire it in.** `gemm_gfx950.py`'s `_store_out_scalar` helper (lines 171-183) is the writeback site for the MVP kernel — currently: `val = ArithValue(val_f32).truncf(out_elem_type)` (round-to-nearest-even, hardware default `arith.truncf` lowering) for non-f32 output. The accumulator is `acc_ty = T.vec(_FRAG_C, T.f32)` with `_FRAG_C = 4` f32 values per lane (`gemm_gfx950.py:53,186-190`), stored one scalar at a time in the epilogue loop (`for i in range_constexpr(_FRAG_C): ... _store_out_scalar(c_div, out_col, val)`, lines 242-279). Since the hardware SR instruction operates on **pairs** (`cvt_sr_pk_bf16_f32(src0, src1, seed) -> v2bf16`), the natural fit is to process the 4 accumulator values as 2 pairs and emit 2 packed-store calls instead of 4 scalar ones when `use_sr=True` — this is a real (if small) restructuring of the epilogue loop, not just a swapped conversion call inside the existing per-scalar loop.

## Phase 0 — Investigation: confirm the intrinsic actually assembles and executes correctly on the box

**Goal:** de-risk the one assumption everything else depends on — that the ROCm toolchain in this environment actually codegens `v_cvt_sr_pk_bf16_f32` correctly from the LLVM intrinsic (or from hand-written inline asm using the same mnemonic).

- [ ] Write a scratch `@flyc.kernel` that calls `llvm.inline_asm` with mnemonic `v_cvt_sr_pk_bf16_f32 $0, $1, $2, $3`, constraints `"=v,v,v,v"`, feeding two known f32 constants and a fixed seed; store the resulting bf16 pair to global memory; run it and confirm the assembler accepts the mnemonic (no "invalid instruction" error) and the result is one of the two bf16 values that bracket each f32 input (the defining property of correct rounding — SR must never produce a value outside the bracket, only choose probabilistically *which* of the two bracketing values with a bias proportional to the fractional distance).
- [ ] If the mnemonic doesn't assemble (toolchain/assembler version mismatch, or the `.td` definition doesn't correspond 1:1 to what this ROCm version's LLVM backend exposes), fall back to investigating whether `FLYDSL_DUMP_IR=1` + a manually-written LLVM IR call to `llvm.amdgcn.cvt.sr.pk.bf16.f32` (via a lower-level intrinsic-call mechanism, if FlyDSL exposes one — check `flydsl/expr/rocdl.py` and MLIR's `llvm.call_intrinsic` op) succeeds where the mnemonic-string inline-asm doesn't.
- [ ] If *neither* path works, fall back to the software technique: bitcast f32 to i32, add a Philox-derived random value scaled to the width of the bits being truncated (16 low bits for bf16, 13 for f16) into the mantissa before an `arith.trunc` — a well-known, purely-arithmetic SR emulation that needs no special instruction. Document which path was taken and why in the final kernel's docstring — do not silently silently swap to software without a comment explaining the hardware path was tried and failed (this is a real fallback, not a shortcut to be taken by default).

**Done when:** a scratch kernel demonstrably produces stochastically-rounded bf16 output from f32 input via *some* working path (hardware-preferred), with the bracketing property spot-checked.

## Phase 1 — Design: portable Philox + epilogue integration shape

**Files:** new `quack/amd/rounding.py` (mirrors `quack/rounding.py`'s module purpose, AMD implementation); `flydsl/expr/rocdl/inline_asm.py` (new wrapper, if Phase 0 confirms the inline-asm path); `quack/amd/gemm_default_epi.py` (real consumer of `sr_seed`, replacing the placeholder comment).

- [ ] `mul_wide_u32(a, b) -> (hi, lo)` reimplemented via `arith.mului_extended(a, b)` — one MLIR op call, no inline asm, no PTX. Confirm the FlyDSL `arith` expr module exposes `mului_extended` at the Python level (it's generated in `_arith_ops_gen.py`; check whether `flydsl/expr/arith.py` re-exports it the way `rocdl/__init__.py` does `from ..._mlir.dialects.rocdl import *` — if not, a one-line import/wrapper addition).
- [ ] `philox(counter, key, n_rounds=7) -> (c0,c1,c2,c3)` — port `quack/rounding.py:92-128` verbatim in structure (same constants `PHILOX_ROUND_A/B`, `PHILOX_KEY_A/B`, same round loop), swapping only the `mul_wide_u32` call site to the new portable version. This function has zero NVIDIA-specific content once the multiply is portable — it's pure `arith` (xor, add) ops.
- [ ] `cvt_sr_pk_bf16_f32(src0_f32, src1_f32, seed_u32) -> v2bf16` — the new FlyDSL wrapper (in `inline_asm.py` or `quack/amd/rounding.py` directly, whichever Phase 0 settles on for the working code path).
- [ ] Epilogue integration shape: add a `use_sr: bool` (or `rounding_mode: str`) parameter to `_build_gemm_16x16` (`gemm_gfx950.py:56`), threaded through to a new pair-wise store path. When `True` and `out_dtype_str == "bf16"`: after computing the 4 per-lane f32 accumulator values (post alpha/beta/bias/activation — SR should be the *last* step before store, same as NVIDIA's design where `convert_f32_to_bf16_sr` is the final downcast), pair them `(acc[0],acc[1])` and `(acc[2],acc[3])`, call the SR-convert twice, store each `v2bf16` result as one 32-bit packed write instead of two scalar 16-bit writes (a nice side benefit: fewer, wider stores). f16 output (`cvt_sr_pk_f16_f32`) follows the identical shape once bf16 is proven.
- [ ] Seed/counter derivation: mirror `quack/rounding.py:convert_f32_to_bf16_sr`'s pattern (`:131-195`) — `counter = (group_idx << 16) | tid`, refresh the Philox batch every 4 pairs, consume one of the 4 returned words per pair. For the GEMM epilogue specifically, `tid` is `fx.thread_idx.x` (already in scope in `_build_gemm_16x16`'s kernel body, `gemm_gfx950.py:101`) and `group_idx` can be the output-tile linear index (`bid_m`/`bid_n`) so different tiles get decorrelated randomness even at the same `tid` — needed since GEMM (unlike a single elementwise kernel) launches many workgroups reusing the same `tid` range. **This decorrelation-by-tile detail has no NVIDIA equivalent to copy from** (`quack/rounding.py`'s SR usage is presumably in a single-tile-covers-everything epilogue context) — design it explicitly, don't silently reuse `tid` alone and risk identical-seed collisions across tiles producing correlated rounding bias.

## Phase 3 — Test strategy (statistical, per the task's framing)

**File:** `tests/amd/test_gemm_sr.py`.

- [ ] **Bracketing property (deterministic, not statistical):** for a set of f32 accumulator values with a known-nonzero bf16 rounding error, run the SR path once and assert the output is one of the two bf16 values immediately above/below the true f32 value (never a third value) — catches gross bugs (wrong seed plumbing, wrong pairing) cheaply before running the expensive statistical test.
- [ ] **Unbiasedness (statistical, the core claim of SR):** fix a single input value `x` with a known fractional part between its two bracketing bf16 representables (e.g. pick `x` such that `bf16_lo`, `bf16_hi` bracket it with a known ratio `p = (x - bf16_lo)/(bf16_hi - bf16_lo)`); run the SR conversion `N` times (N large, e.g. 10⁴–10⁵) with *different* seeds/counters (vary `tid`/tile-index inputs, not just re-running the same kernel launch — reuse the decorrelation design from Phase 1); assert `mean(outputs) ≈ x` within a tolerance that shrinks with `1/sqrt(N)` (standard Monte Carlo error bound — pick `N` large enough that the tolerance is comfortably tighter than `bf16_hi - bf16_lo`, so the test actually distinguishes "correctly stochastic" from "always rounds to nearest" or "always rounds down"). This is the test that would catch e.g. an off-by-one in the Philox counter causing every lane to get the same random bits (which would make SR degenerate into deterministic rounding — a real, plausible bug mode given the tile-decorrelation design is new, hand-written code with no NVIDIA precedent to copy).
- [ ] **RN-vs-SR mean comparison on a full GEMM:** run the same `A@B` through `use_sr=False` and `use_sr=True` (averaged over many seeds) and confirm both converge to the same `A.float()@B.float()` reference within their respective expected error bounds — SR's *mean* error should be lower than or comparable to RN's fixed bias for values that sit consistently on one side of the bf16 grid (this is stochastic rounding's actual practical benefit for training — unbiased accumulated error over many updates — so the test should demonstrate it, not just "doesn't crash").
- [ ] **Regression guard:** `use_sr=False` output byte-identical to a pre-this-plan build (or simply: identical to `.truncf()`-based output computed independently in the test) — confirms the default path is unaffected.
